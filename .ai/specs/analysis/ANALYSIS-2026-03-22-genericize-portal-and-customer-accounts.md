# Pre-Implementation Analysis: Genericize Portal Identity Layer

## Executive Summary

The spec is well-structured and covers the core rename surface comprehensively. However, it has **6 gaps** that would cause build failures or runtime errors if not addressed: missing notification type IDs, i18n locale files, search config, custom entity declarations, subscriber/worker metadata, and `modules.ts` registration. All are straightforward additions. No deprecation bridges needed per user directive (no external consumers). **Ready to implement after gap fixes.**

## Gap Analysis

### Critical Gaps (Block Implementation)

**Gap #1 — Notification Type IDs**: The spec does not mention renaming notification type IDs. The module declares 2 notification types:
- `customer_accounts.user.signup` → `portal_accounts.user.signup`
- `customer_accounts.user.locked` → `portal_accounts.user.locked`

These are stored in DB and referenced by subscribers. The `notifications.ts` file must be updated, and notification links (`/backend/customer_accounts/{id}`) must change to `/backend/portal_accounts/{id}`.

**Add to Phase 3**: Update `notifications.ts` — rename type IDs and link paths.
**Add to Phase 5**: DB migration to update stored notification `type` values.

**Gap #2 — i18n Locale Files**: The module has locale files (`locales/en.json`, `de.json`, `es.json`, `pl.json`) with keys namespaced under `customer_accounts.*`. These keys are used in:
- Notification title/body templates: `customer_accounts.notifications.*`
- Backend page titles and labels
- ACL feature display names

**Add to Phase 3**: Rename locale file keys from `customer_accounts.*` → `portal_accounts.*`.

**Gap #3 — Search Config**: `search.ts` declares searchable entities with IDs like `customer_accounts:customer_user`. The entity type IDs and search badges need updating.

**Add to Phase 3**: Update `search.ts` — entity type IDs and search badge labels.

**Gap #4 — Custom Entity Declarations**: `ce.ts` declares custom entities with IDs prefixed by the module name. Entity IDs like `customer_accounts:customer_user` are used in the entity-fields registry.

**Add to Phase 3**: Update `ce.ts` — entity IDs to use `portal_accounts` prefix.

**Gap #5 — Subscriber & Worker Metadata**: Subscribers have `metadata.event` pointing to old event IDs. Workers have `metadata.queue` set to `customer_accounts`. These must be updated:
- Subscriber: `notifyStaffOnSignup` → event: `portal_accounts.user.created`
- Workers: `cleanupExpiredSessions`, `cleanupExpiredTokens` → queue: `portal_accounts`

**Add to Phase 3**: Update subscriber `metadata.event` values and worker `metadata.queue` values.

**Gap #6 — `modules.ts` Registration**: `apps/mercato/src/modules.ts` registers the module as `{ id: 'customer_accounts', from: '@open-mercato/core' }`. This is the authoritative module ID source.

**Add to Phase 4**: Update `apps/mercato/src/modules.ts` — change ID to `portal_accounts`.

### Important Gaps (Should Address)

**Gap #7 — `modules:prepare` Step**: The spec mentions `yarn generate` but not `npm run modules:prepare` which is the canonical command that triggers generation after module file changes. Add explicit step.

**Gap #8 — `clientBroadcast` Events**: Some events have `clientBroadcast: true` (not just `portalBroadcast`). The spec's event table only lists `portalBroadcast` events. Two events broadcast to the admin backend:
- `customer_accounts.user.created` (`clientBroadcast: true`)
- `customer_accounts.invitation.accepted` (`clientBroadcast: true`)

These are renamed correctly in the spec's event mapping table but the broadcast flag distinction should be noted for testing — admin backend listeners may pattern-match on event ID prefixes.

**Gap #9 — Enrichers**: The module has `data/enrichers.ts`. The generated `enrichers.generated.ts` imports from `customer_accounts/data/enrichers`. After folder rename + `yarn generate`, this auto-resolves, but the enricher code itself may reference `customer_accounts` entity types internally.

**Add to Phase 3**: Review and update `data/enrichers.ts` internal references.

**Gap #10 — API Interceptors**: The module has `api/interceptors.ts`. Same pattern as enrichers — auto-resolved by generator but internal references may need updating.

**Add to Phase 3**: Review and update `api/interceptors.ts` internal references.

### Nice-to-Have Gaps

**Gap #11 — Existing Specs**: Several specs in `.ai/specs/` reference `customer_accounts` and `Customer*` types. The spec mentions updating these in Phase 5 step 8 but doesn't list them. Key specs:
- `SPEC-060-2026-03-04-customer-identity-portal-auth.md`
- Any other spec referencing the module
