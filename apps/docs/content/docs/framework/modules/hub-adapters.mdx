# Hub Adapter Registry

A **hub** is a typed adapter registry created by `defineHub<T>()`. It replaces hand-rolled Maps, singleton registries, and global arrays with a single API that supports auto-discovery, versioning, and cross-package sharing.

The platform ships one built-in hub (`data_sync`). You can create your own for any adapter pattern — payment gateways, shipping carriers, notification channels, etc.

```ts title="How it looks end-to-end"
// 1. Define the hub (once)
const paymentHub = defineHub<PaymentAdapter>({ id: 'payments' })

// 2. Provider registers (auto or manual)
paymentHub.register(stripeAdapter)

// 3. Consumer resolves
const adapter = paymentHub.get('stripe')
```

## Creating a Hub

### Define the adapter interface

Every adapter must carry a string key so the hub can index it. By default the field is `providerKey`, but you can customize it.

```ts title="src/modules/payments/lib/adapter.ts"
import type { AdapterContext } from '@open-mercato/shared/lib/hub'

export interface PaymentAdapter {
  readonly providerKey: string
  charge(amount: number, currency: string, ctx?: AdapterContext): Promise<{ transactionId: string }>
  refund(transactionId: string, ctx?: AdapterContext): Promise<void>
}
```
### Create the hub

One line. Export it so providers and consumers can import it.

```ts title="src/modules/payments/lib/adapter-registry.ts"
import { defineHub } from '@open-mercato/shared/lib/hub'
import type { PaymentAdapter } from './adapter'

export const paymentHub = defineHub<PaymentAdapter>({ id: 'payments' })
```

Options:

| Option | Default | Description |
|--------|---------|-------------|
| `id` | *(required)* | Unique hub identifier. Same id = same backing store across packages. |
| `adapterKeyField` | `'providerKey'` | The property name used to extract the adapter's lookup key. |
| `versioned` | `false` | Enable versioned registration (multiple versions per key). |
### Use the hub in your API routes

```ts title="src/modules/payments/api/post/charge.ts"
import { paymentHub } from '../../lib/adapter-registry'

export default async function handler(req, res) {
  const adapter = paymentHub.get(req.body.provider)
  if (!adapter) {
    return res.status(400).json({ error: 'Unknown payment provider' })
  }
  const result = await adapter.charge(req.body.amount, req.body.currency)
  return res.json(result)
}
```

## Registering Providers

### File structure rule

| File | Exports | Purpose |
|------|---------|---------|
| `lib/adapter.ts` | Adapter **class** | Implementation lives here |
| `integration.ts` | Adapter **instance** (`export const adapter = new MyAdapter()`) | Generator reads this — auto-registered at bootstrap |

Never put business logic in `integration.ts`. It only imports the class from `lib/` and exports the instance.

### Preferred: Export from `integration.ts`

The generator reads `adapter` (or `adapters`) exports from every module's `integration.ts` and wires them into the bootstrap sequence. No manual registration code needed.

```ts title="packages/provider-stripe/src/modules/gateway_stripe/lib/adapter.ts"
import type { PaymentAdapter } from '@open-mercato/core/modules/payments/lib/adapter'
import type { AdapterContext } from '@open-mercato/shared/lib/hub'

export class StripePaymentAdapter implements PaymentAdapter {
  readonly providerKey = 'stripe'

  async charge(amount: number, currency: string, ctx?: AdapterContext) {
    ctx?.logger.info('Charging via Stripe', { amount, currency })
    // Stripe API call — credentials injected at call-time by the hub service
    return { transactionId: '...' }
  }

  async refund(transactionId: string, ctx?: AdapterContext) {
    ctx?.logger.info('Refunding via Stripe', { transactionId })
    // ...
  }
}
```

```ts title="packages/provider-stripe/src/modules/gateway_stripe/integration.ts"
import { StripePaymentAdapter } from './lib/adapter'

export const integration = {
  id: 'gateway_stripe',
  hub: 'payments',
  providerKey: 'stripe',
  title: 'Stripe',
  credentials: { fields: [/* ... */] },
  healthCheck: { service: 'stripeHealthCheck' },
}

// Import from lib, export here — generator picks it up automatically
export const adapter = new StripePaymentAdapter()
```

At bootstrap, the platform calls `paymentHub.register(adapter)` automatically. The adapter implementation stays in `lib/adapter.ts` — `integration.ts` only re-exports the instance.

### Versioned adapters

Export an `adapters` array when shipping multiple API versions:

```ts title="packages/provider-stripe/src/modules/gateway_stripe/integration.ts"
import { StripeAdapterV2025 } from './lib/adapters/v2025'
import { StripeAdapterV2024 } from './lib/adapters/v2024'

export const adapters = [
  { adapter: new StripeAdapterV2025(), version: '2025-02-24' },
  { adapter: new StripeAdapterV2024(), version: '2024-12-18' },
]
```

The first-registered version becomes the default when `hub.get('stripe')` is called without a version.

### Manual registration

For adapters that depend on DI services, register from `di.ts` or `setup.ts`:

```ts title="src/modules/my_provider/di.ts"
import { paymentHub } from '@open-mercato/core/modules/payments/lib/adapter-registry'

export function register(container) {
  const adapter = {
    providerKey: 'my_provider',
    async charge(amount, currency, ctx?) {
      const client = ctx?.resolve('myProviderClient') ?? container.resolve('myProviderClient')
      return client.charge(amount, currency)
    },
    async refund(transactionId, ctx?) {
      const client = ctx?.resolve('myProviderClient') ?? container.resolve('myProviderClient')
      return client.refund(transactionId)
    },
  }
  paymentHub.register(adapter)
}
```

## Common Patterns

### Hub Service Layer

Never call `hub.get()` directly from API routes. Wrap it in a service that handles credentials, logging, and errors. This is the standard pattern for every hub.

```ts title="src/modules/payments/lib/payment-service.ts"
import { paymentHub } from './adapter-registry'
import type { CredentialsService } from '../../integrations/lib/credentials-service'
import type { IntegrationLogService } from '../../integrations/lib/log-service'

interface TenantScope {
  tenantId: string
  organizationId: string
}

export function createPaymentService(deps: {
  credentialsService: CredentialsService
  logService: IntegrationLogService
}) {
  return {
    async charge(providerKey: string, amount: number, currency: string, scope: TenantScope) {
      // 1. Resolve adapter
      const adapter = paymentHub.get(providerKey)
      if (!adapter) throw new Error(`No payment adapter for "${providerKey}"`)

      // 2. Fetch tenant-scoped credentials
      const credentials = await deps.credentialsService.resolve(providerKey, scope)

      // 3. Execute with logging
      const startedAt = Date.now()
      try {
        const result = await adapter.charge(amount, currency)
        await deps.logService.success(providerKey, { duration: Date.now() - startedAt })
        return result
      } catch (error) {
        await deps.logService.failure(providerKey, { error, duration: Date.now() - startedAt })
        throw error
      }
    },

    async refund(providerKey: string, transactionId: string, scope: TenantScope) {
      const adapter = paymentHub.get(providerKey)
      if (!adapter) throw new Error(`No payment adapter for "${providerKey}"`)
      await deps.credentialsService.resolve(providerKey, scope)
      return adapter.refund(transactionId)
    },
  }
}
```

## Adapter Context

Adapters that perform I/O (network calls, database access, logging) can receive an optional `AdapterContext` parameter. The context is built by the framework caller (sync engine, API route, hub service) and passed to every adapter method that opts in.

### Type definition

```ts
import type { AdapterContext } from '@open-mercato/shared/lib/hub'

export type AdapterLogger = {
  info(message: string, data?: Record<string, unknown>): void
  warn(message: string, data?: Record<string, unknown>): void
  error(message: string, data?: Record<string, unknown>): void
  debug(message: string, data?: Record<string, unknown>): void
}

export type AdapterContext = {
  resolve: <T = unknown>(name: string) => T
  logger: AdapterLogger
  scope: {
    organizationId: string
    tenantId: string
  }
}
```

### Constructing context

Framework callers build the context from the DI container and current request scope:

```ts
import type { AdapterContext } from '@open-mercato/shared/lib/hub'

const ctx: AdapterContext = {
  resolve: <T = unknown>(name: string) => container.resolve(name) as T,
  logger: { info: ..., warn: ..., error: ..., debug: ... },
  scope: { organizationId: auth.orgId, tenantId: auth.tenantId },
}
```

### Using context in adapters

Adapter methods declare `ctx?` as an optional trailing parameter. Methods that need DI or logging use it; methods that don't simply ignore it:

```ts
async *streamImport(input, ctx) {
  const em = ctx!.resolve<EntityManager>('em')
  ctx!.logger.info('Starting import', { entityType: input.entityType })
  // ...
}

async getMapping(input) {
  // Methods that don't need DI simply ignore ctx
  return { entityType: input.entityType, fields: [], matchStrategy: 'externalId' }
}
```

### Comparison with other extension point contexts

| Extension Point | Context Type | Key Fields |
|---|---|---|
| Worker | `JobContext` | `jobId`, `attemptNumber`, `queueName` |
| Subscriber | `SubscriberContext` | `resolve`, `eventName?` |
| Workflow | `WorkflowTools` | `resolve`, `logger`, `run`, `step`, `emitToEventBus` |
| Hub Adapter | `AdapterContext` | `resolve`, `logger`, `scope` |

Subscribers, workflows, and hub adapters provide `resolve` for DI access. Workers receive job metadata but access DI through a separate `HandlerContext` extension. `AdapterContext` adds `scope` for tenant isolation and `logger` for structured logging.

### DI Wiring for Hub Services

Register the service via Awilix so API routes resolve it from the container:

```ts title="src/modules/payments/di.ts"
import { asFunction } from 'awilix'
import { createPaymentService } from './lib/payment-service'

export function register(container: AppContainer) {
  container.register({
    paymentService: asFunction(({ credentialsService, integrationLogService }) =>
      createPaymentService({
        credentialsService,
        logService: integrationLogService,
      })
    ).singleton(),
  })
}
```

API routes stay thin:

```ts title="src/modules/payments/api/post/charge.ts"
const service = container.resolve('paymentService')
const result = await service.charge(providerKey, amount, currency, { tenantId, organizationId })
```

### Bundle Providers

When one provider package covers multiple entity types (e.g., Shopify products + orders), export a bundle with a single adapter:

```ts title="packages/sync-shopify/src/integration.ts"
import type { IntegrationBundle, IntegrationDefinition } from '@open-mercato/shared/modules/integrations/types'

export const bundle: IntegrationBundle = {
  id: 'sync_shopify',
  title: 'Shopify',
  credentials: { fields: [{ key: 'api_key', label: 'API Key', type: 'password' }] },
}

export const integrations: IntegrationDefinition[] = [
  { id: 'sync_shopify_products', hub: 'data_sync', providerKey: 'shopify', bundleId: 'sync_shopify', title: 'Products' },
  { id: 'sync_shopify_orders', hub: 'data_sync', providerKey: 'shopify', bundleId: 'sync_shopify', title: 'Orders' },
]

// One adapter handles all entity types — routes internally by entityType
export const adapter = new ShopifyDataSyncAdapter()
```

All integrations in a bundle share the same `hub` and `providerKey`. The generator extracts one adapter registration for the group.

### Health Checks

Health checks stay in `di.ts` — they're DI services, not hub adapters:

```ts title="packages/provider-stripe/src/di.ts"
import { asFunction } from 'awilix'

export function register(container: AppContainer) {
  // Only DI services — no adapter registration (that's in integration.ts)
  container.register({
    stripeHealthCheck: asFunction(({ credentialsService }) => ({
      async check(scope: TenantScope) {
        const creds = await credentialsService.resolve('stripe', scope)
        const response = await fetch('https://api.stripe.com/v1/balance', {
          headers: { Authorization: `Bearer ${creds.secret_key}` },
        })
        return { ok: response.ok }
      },
    })).singleton(),
  })
}
```

Reference the health check in `integration.ts`:

```ts title="integration.ts"
export const integration = {
  id: 'stripe_payments',
  hub: 'payments',
  providerKey: 'stripe',
  healthCheck: { service: 'stripeHealthCheck' },
}
```

## Architecture

Three layers — the hub is the thin registry in the middle:

```
┌─────────────────────────────────────────────────────────┐
│  API Route                                              │
│  const result = await paymentService.charge(...)        │
├─────────────────────────────────────────────────────────┤
│  Hub Service (orchestration)                            │
│  credentials → adapter.charge() → logging               │
├─────────────────────────────────────────────────────────┤
│  Hub Registry (defineHub)                               │
│  paymentHub.get('stripe') → StripeAdapter               │
├─────────────────────────────────────────────────────────┤
│  Provider (integration.ts)                              │
│  export const adapter = new StripeAdapter()             │
└─────────────────────────────────────────────────────────┘
```

Provider registration flow:

```
integration.ts ─── export adapter ──→ Generator ──→ Bootstrap ──→ Hub (Symbol.for Map)
                                                                       ↑
                                                            hub.get() ─┘ ← Hub Service ← API Route
```

## API Reference

### `defineHub<T>(options): Hub<T>`

```ts
import { defineHub } from '@open-mercato/shared/lib/hub'
```

Returns a frozen `Hub<T>` object with these methods:

| Method | Signature | Description |
|--------|-----------|-------------|
| `register` | `(adapter: T, options?: { version?: string }) => () => void` | Registers an adapter. Returns a dispose function that removes it. |
| `get` | `(key: string, version?: string) => T \| undefined` | Retrieves an adapter by key. For versioned hubs, falls back to the default version when the requested version is not found. |
| `list` | `() => T[]` | Returns all registered adapters. Versioned hubs deduplicate — one entry per provider key. |
| `clear` | `() => void` | Removes all adapters. Intended for test teardown. |

The `id` property is also exposed as a readonly string.

> **Note:** `register()` returns a **dispose function**. Call it to remove a single adapter without clearing the entire hub.

### Custom key field

If your adapter interface uses a different property name:

```ts
const carrierHub = defineHub<CarrierAdapter>({
  id: 'shipping_carriers',
  adapterKeyField: 'carrierId',
})
```

### Versioned hubs

```ts
const hub = defineHub<MyAdapter>({ id: 'my_hub', versioned: true })

hub.register(adapterV1, { version: '1.0' })
hub.register(adapterV2, { version: '2.0' })

hub.get('my_key')          // returns adapterV1 (first registered = default)
hub.get('my_key', '2.0')   // returns adapterV2
hub.get('my_key', '99.0')  // falls back to adapterV1
hub.list()                  // returns [adapterV1] (deduped, one per key)
```

## Testing

Use `hub.clear()` in `afterEach` to prevent state leaking between tests:

```ts
import { paymentHub } from '../lib/adapter-registry'

afterEach(() => {
  paymentHub.clear()
})

it('resolves the stripe adapter', () => {
  const adapter = { providerKey: 'stripe', charge: jest.fn(), refund: jest.fn() }
  paymentHub.register(adapter)

  expect(paymentHub.get('stripe')).toBe(adapter)
})
```

For scoped cleanup (single adapter), use the dispose function:

```ts
it('removes adapter on dispose', () => {
  const dispose = paymentHub.register(myAdapter)
  dispose()
  expect(paymentHub.get('my_provider')).toBeUndefined()
})
```

## How It Works

The backing store uses `Symbol.for('@open-mercato/hub/<id>')` on `globalThis`. Two `defineHub()` calls with the same `id` — even from different packages — share the same `Map`. This is what makes cross-package registration work without an explicit import chain.

At build time, the generator extracts `adapter`/`adapters` exports from each module's `integration.ts`. At app startup, the bootstrap factory iterates these entries, clears each referenced hub, and calls `hub.register(adapter)` for every discovered adapter. This means providers just need to export — no registration boilerplate.
